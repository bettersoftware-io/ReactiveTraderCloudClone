# B3c bring-your-own model keys Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in person can run Jarvis on their own Anthropic, OpenRouter or OpenAI key, under their own daily limit, and both web clients send a Content-Security-Policy.

**Architecture:** A brain stays one string, so the wire, the preference and the picker keep their shape: an own-key brain is `own:<provider>:<model>`, drawn from a curated list in `@rtc/domain`. The key lives in the browser, reaches the server in a `jarvis.key` frame after each connect, and stays in one object scoped to that socket. Each key gets its own `AgentLoop` for the connection: the existing Anthropic loop, then a new OpenAI-compatible loop in PR 4.

**Tech Stack:** TypeScript, RxJS, rx-ws-effects, Anthropic SDK, plain `fetch` for the OpenAI-compatible loop, Vercel headers, Playwright.

**Spec:** [B3 design §5](../specs/2026-10-25-b3-ai-metering-byo-keys-design.md#5-b3c--bring-your-own-key), decisions D9–D11 and D13–D19, with [hardening §10](../specs/2026-09-27-public-launch-hardening-design.md#10-bring-your-own-model-keys-findings-2026-09-29-for-b3).

## How this ships: four PRs

The spec's D12 calls B3c one PR. This plan proposes four, because a reviewer could reject any one and accept the rest, and each works alone once deployed.

| PR | Branch | What | Deploy |
|---|---|---|---|
| 1 | `b3c-csp` | The CSP (Task 1) | both web clients |
| 2 | `b3c-server` | Brain vocabulary, `jarvis.key`, own-key budget, Anthropic own keys (Tasks 2–6) | server; old clients are unaffected |
| 3 | `b3c-clients` | Key storage, the three cores, indicators, Preferences, picker (Tasks 7–11) | both web clients |
| 4 | `b3c-openai-loop` | OpenAI-compatible loop, OpenRouter and OpenAI (Tasks 12–14) | server, then both web clients |

Merge in order. PR 3 is the first a person can see; after PR 3, Anthropic own keys work end to end.

## Global Constraints

- A key is never stored on the server in any form, and never appears in a log line, an error payload, a URL, `history.state`, a `data-*` attribute, or the DOM after entry.
- The client sends a provider id from a closed set; the server maps it to a fixed host. No free-text endpoint and no free-text model field.
- Hosts: `api.anthropic.com`, `openrouter.ai`, `api.openai.com`.
- Key storage: sessionStorage by default, localStorage with "Remember on this device". Wiped at sign-out, on an account switch, and on a session ended by the server. Never encrypted in the browser.
- Shown back masked (`sk-ant-…a1b2`) with Replace and Remove.
- Daily cap on an own key: default **$1**, adjustable, or "no limit". Per person, not per key.
- One own key per person at a time; a key for another provider replaces it (D14).
- With a cap, a spend store that cannot be reached puts the person on scripted. With "no limit" the turn runs and spend is recorded best effort (D15).
- Own keys work when the house key is off (D16).
- Own-key turns skip the house budget and the house cap; server rate limits and chat caps still apply.
- A failing own key fails the turn with a message naming the provider, and never falls back to the house key (D13).
- Narrator turns on an own-key brain run on that brain and count against the own cap (D19).
- With a key set the picker shows "House key" and "Your key" groups (D18).
- Demo-roster logins never see the key section. React Native is out of scope.
- `.module.css` files in `client-react` and `client-solid` stay byte-identical.
- One outward step per Bash call. Commit trailers per the session's attribution reminder.

## Review Focus

Most likely to bite first. Each line has a named test in the owning task.

1. **The tab was closed, or the socket reconnected, and the saved brain is an own-key brain.** The key is gone or not yet accepted. The turn must run scripted, never on the house key. Spec D13 and D5 cover failures, not absence. (Tasks 5, 7)
2. **An inspector is attached, or a recording is saved.** `instrumentWsAdapter` mirrors every outgoing frame to the devtools hub, in production builds too, so the key frame must be redacted before it reaches the hub. (Task 8)
3. **A key frame is sent while the socket is closed.** `WsAdapter` queues it and flushes it on a later open, possibly after sign-out or for another account. Key frames must never enter the queue. (Task 8)
4. **A key is rejected in the middle of a session.** The own brain stays selected and each turn fails with the clear message, until the person replaces the key or picks another brain. It must not slide to a house brain. (Tasks 5, 7)
5. **A client hammers `jarvis.key`, or guesses keys.** Each new key makes the server call a provider, so checks are limited per caller, and a socket that closes mid-check keeps nothing. (Task 4)
