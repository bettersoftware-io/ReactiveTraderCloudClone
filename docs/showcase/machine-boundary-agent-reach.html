Jarvis P5 · app-driving + proactive narrator · 2026-08-05

The agent's reach was exactly the machine boundary.

When an AI-driving tool arrived, it could touch everything already behind an intent — and nothing that wasn't. The gap between "Jarvis can do this" and "Jarvis can't" turned out to be a map of one design decision, made months before any AI was in the picture.

The claim

Every AI-era capability this app has shipped — tool-calling over live domain data, an external agent operating the app over MCP, generative UI bound to live streams, now driving the app directly and speaking up unprompted — fell out of clean-architecture decisions none of which were made "for AI." — 2026-07-12 Jarvis AI assistant design, §2

The natural experiment

This round is the sharpest test of that claim yet, because it is falsifiable in a very concrete way: give an agent a closed vocabulary of UI-driving commands, then look at what it can and cannot reach. Everything living behind a state machine — the equities workspace, panel layout, preferences — was drivable with zero new state code. The only unreachable state was the state that had never been promoted off useState.

REACHABLE, DAY ONE

  • Workspace layout — maximize/restore/collapse/expand, via the existing per-tab layout machine
  • Equities chart — symbol, timeframe, chart type, indicators, panes, via EqWorkspaceMachine
  • Theme + power-saver — via their existing preference presenters
  • Panels — dismiss, via JarvisPanelsMachine (spawn/edit already owned by R1's render_panel)
All four were already machines. Wiring drive_app to them was new dispatch code, not new state.

UNREACHABLE

  • Workspace tab (App.tsx) — a bare useState<WorkspaceTab>, no path from the composition root. Promoted this round — see below.
  • FxViewProvider — rates/blotter sub-tabs + quick filter, still three useState calls. Deliberately left as-is — the still-unreachable exhibit.
Two pockets, found by asking "what can't the driver reach" — not by auditing the codebase for useState first.

The toll — one promotion, not a rewrite

The workspace tab was worth promoting: it gates which module the whole desk shows, and the flagship demo needs Jarvis to switch to Equities. The entire migration cost was one small machine plus the two-line rewire it took in each web client's App.tsx.

Before — unreachable
packages/client-react/src/ui/App.tsx
// nothing outside this component can ever move activeTab —
// there is no path from the composition root to setActiveTab
const [activeTab, setActiveTab] = useState<WorkspaceTab>("fx");

// ...
<HeaderChrome activeTab={activeTab} onTabChange={setActiveTab} />
<WorkspaceEngine key={activeTab} tab={activeTab} />
After — driven and clicked, same intent
packages/client-react/src/ui/App.tsx
// the promoted composition-root singleton — the ONLY
// state promotion this whole round makes
const { useWorkspaceNav } = useViewModel();
const { state: navState, switchTab } = useWorkspaceNav();
const activeTab = navState.activeTab;

// ...
<HeaderChrome activeTab={activeTab} onTabChange={switchTab} />
<WorkspaceEngine key={activeTab} tab={activeTab} />
Two callers, one intent: a nav-rail click and JarvisDriverMachine's switchTab command handler now call the exact same method on the exact same WorkspaceNavMachine singleton. "The UI can do it" and "Jarvis can do it" are one fact, not two kept in sync by hand.
1
new machine — WorkspaceNavMachine, ~70 lines, no injected deps
2
rewired components — App.tsx in each web client (React, Solid)
0
changes to HeaderChrome's own props — its onTabChange slot already took any callback

Still unreachable, on purpose

The round deliberately left a second useState pocket exactly as it was, as the exhibit for what "the boundary" costs when it isn't paid.

NOT PROMOTED — DEFERRED BY DESIGN
packages/client-react/src/ui/fx/FxViewProvider.tsx
const [ratesTab, setRatesTab] = useState<RatesTab>("rates");
const [blotterTab, setBlotterTab] = useState<BlotterTab>("trades");
const [quickFilter, setQuickFilter] = useState("");

Jarvis cannot switch the FX rates/blotter sub-tab or set the quick filter today — and that gap is the point, not an oversight. The boundary stays visible in what the agent can and cannot do, rather than being quietly promoted away. Same one-line fix as App.tsx when it earns its turn; tracked as a deferred item, not a bug.

The counterfactual

A hooks-era codebase

Every screen's state is the App.tsx case: local, component-owned, no seam for anything outside the tree to reach in. "An AI drives the app" means auditing every screen for useState, then rewriting the state layer underneath the whole UI.

vs

Here

State already lived behind intents everywhere the doctrine had been followed. Reaching it from an AI was a typed dispatcher over the existing machines. The two places it wasn't followed were exactly the two places the agent couldn't reach — and promoting one took an afternoon.
