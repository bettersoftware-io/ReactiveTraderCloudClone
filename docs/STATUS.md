- **Prototype ↔ data-model mismatches (adapt the model to the UI, not only the UI to the model)** — the Phase 5 design records **seven** places where the mobile-v1 prototype asks for something the domain/seam cannot express, and each is currently resolved by contorting the UI. That is the right default for a presentation rehaul but not automatically the right answer: several exist only because the domain was shaped for the desktop product's information architecture. Ledger (spec §8, with per-item workaround vs. model-change): **M1** sell-side has no "quotes I submitted" history projection; **M2** `CreateRfqInput.dealerIds` is required though the prototype has no dealer-picker; **M3** RFQ window is 120 s in the domain vs 45 s in the prototype (a 120 s ring barely moves on a phone); **M4** equities has no tick-history stream, so sparklines must be derived from OHLC candles; **M5** a fill is only a binary animation intent, with no order-lifecycle event carrying qty/price/outcome; **M6** `AnalyticsSimulator` emits the same frozen `STATIC_POSITIONS` constant on every emission, and **two of the Analytics screen's three widgets read it** (pair P&L bars, exposure bubbles) — so both the bars' 800 ms tween and the bubbles' 900 ms breathing would fire once on mount and never again, leaving most of 5c's motion work observable only inside a pinned golden; **M7** analytics history appends every 10 s against the prototype's 1 s mock cadence. **M6 is the one to weigh first** — cheap, confined to a simulator, and it decides whether most of 5c's motion work is worth doing at all. None of these are in Phase 5's scope; each is a candidate follow-up that would let a later pass *simplify* the UI rather than keep working around the gap. **All seven are SHARED, not RN-only** — every one lives in `@rtc/domain`/`@rtc/client-core`, below the UI and above both clients, so a model fix serves web and RN at once (the web analytics bars read the same frozen `STATIC_POSITIONS`; web merely never animates them, so nothing visibly fails to move). By contrast the *rendering* wrinkles — Reanimated worklets, regular-weight-only Skia text, unported `shadowBlur` bloom, the dev-client/simulator dependency — are RN-only with no web analogue. **Separately tracked as R1 (a gap against the REFERENCE implementation, not the prototype):** Adaptive's ReactiveTraderCloud analytics **exposure bubbles are draggable** (force-directed sim + drag behaviour); ours are inert in **both** clients — verified: no pointer/mouse/touch handler anywhere in `client-react`'s (or `client-solid`'s) `PositionsPanel`, and RN's are a static shelf-packed layout. Dragging is interaction, not decoration — it is how a user pulls a crowded bubble out to read it, most valuable exactly where our layouts are weakest. Cheaper than first recorded: an earlier draft claimed drag threatens pinned goldens — **that was wrong**. What threatens a golden is a force-directed simulation *settling over time*, not drag; a golden never drags, so an un-dragged layout is exactly as stable as today's (and the harness could disable drag outright). Keep the deterministic shelf-packed layout and add drag on top. - **Blank line between adjacent multi-line "block" statements — PARKED (investigated, no rule adopted).** Spun off from the `rtc/newspaper-order` extension (PR #287) that now pushes `jest.mock`/`jest.unmock` below the tests like `vi.mock` (both are hoisted above imports by their runners, so position is behaviour-neutral). The newspaper autofix already *separates* the mocks it moves (it joins them with a blank line), but there is **no rule that enforces a blank line between adjacent multi-line blocks in general** — e.g. two `jest.mock(…, () => {…})` factories authored already-at-the-bottom, packed with no separator. Goal was a *generic, size-based* rule ("if a statement spans more than ~2–3 lines, separate it"), **not** an identifier-based mock-only one. Findings: **(1) Biome cannot do it** — the maintainers deliberately don't implement `padding-line-between-statements`; blank-line *insertion* is classed as formatting, and the Biome formatter only preserves/collapses blank lines, never inserts required ones ([biomejs/biome#3016](https://github.com/biomejs/biome/discussions/3016)). **(2) ESLint can, via the existing `padding-line-between-statements`** (already in `eslint.config.mjs`): the `multiline-expression` selector matches exactly the missing case — multi-line call statements ending in `)` (like `jest.mock(…)` / `describe(…)`) that the current `multiline-block-like` clause misses because they don't end in `}`. Config would be one clause: `{ blankLine: "always", prev: "multiline-expression", next: "multiline-expression" }`. **(3) But its blast radius is large and imprecise** — measured on the repo it flags **350 spots across 152 files** (120 test, 32 production), all autofixable, with two false-positive modes: **(a)** simple statements that merely *wrapped* because they were long (e.g. a 3-line `expect(headers.get("CT")).toBe("application/json")`) get split from the next assertion — same spirit as the "don't separate one-liners" objection; **(b)** production RxJS assignment chains (`this.x$ = src.pipe(…)`) get separated field-by-field. Root cause: no built-in selector expresses *"a call whose **argument** is a real block / object-literal body"* — `multiline-block-like` keys on a trailing `}`, `multiline-expression` on any 2+-line span; the granularity is binary (single- vs multi-line), with no line-count threshold. **Options if revived:** (i) accept the generic `multiline-expression` clause (repo-wide, or scoped to `**/*.{spec,test}.{ts,tsx}` to spare production RxJS) and live with the wrapped-statement noise; (ii) write a small autofixable custom `rtc/` rule that fires only between multi-line statements whose body is an actual block/object-literal (exempting merely-wrapped ones) — precise, matches the "block" intent, but new code to maintain; (iii) do nothing and rely on the newspaper-order autofix for the common (moved-mock) case. **Parked** until it recurs / annoys enough to justify option (i) or (ii).
- **CI typecheck flake — two concurrent `tsc` processes share one `.tsbuildinfo` per package (diagnosed, NOT fixed).** Observed on PR #373 run [30204813551 attempt 1](https://github.com/bettersoftware-io/ReactiveTraderCloudClone/actions/runs/30204813551/attempts/1): the `Typecheck` step failed with ~40 `error TS2305: Module '"@rtc/client-core"' has no exported member '…'` — *every* symbol missing, not one — followed by `Segmentation fault (core dumped)` and exit 139. A rerun of the identical SHA was green, so it reads as "infrastructure". **It is not.** The causal chain, from the log timings: `tsconfig.base.json` sets `"composite": true` for every package, and each package pins a single `"tsBuildInfoFile": "dist/tsconfig.tsbuildinfo"`. `turbo.json` declares `typecheck.dependsOn: ["^build"]` — *upstream* build, **not the package's own** — so `@rtc/client-core:typecheck` (`tsc --noEmit`) and `@rtc/client-core:build` (`tsc --build`) start concurrently in the same directory (both at `13:51:33` in the log) and, because `composite` implies `incremental`, **both read and write that one `dist/tsconfig.tsbuildinfo`**. Downstream, `react-bindings`, `solid-bindings` and `ui-contract` each carry a TS project reference to `../client-core` and each runs its own `tsc --build` (`13:51:44`, `13:51:45`, `13:51:47`), so each consults that same buildinfo and will *rebuild client-core*, truncating and rewriting `packages/client-core/dist/*.d.ts`, if it reads as stale or corrupt. `@rtc/client-react-native:typecheck` started at `13:51:56` and read the `.d.ts` mid-rewrite — hence every export missing at once. A concurrently-written buildinfo is also a known `tsc` segfault trigger, which accounts for the 139. **Why it stays open:** the fix touches the build graph for *every* package and the cheap options trade off against each other — (a) `typecheck.dependsOn: ["^build", "build"]` is a one-line turbo change and provably removes the overlap, but serialises typecheck behind build and would make a bare `pnpm typecheck` trigger full builds (a daily-loop cost that needs an explicit call); (b) giving `--noEmit` its own buildinfo (`tsc --noEmit --tsBuildInfoFile .turbo/typecheck.tsbuildinfo`) keeps both tasks parallel and costs the daily loop nothing, but needs editing ~12 package scripts — **probed and viable**: TypeScript 6.0.3 accepts that flag pair alongside `composite: true` and exits 0 in `packages/client-core`, so the option is validated rather than assumed; (c) dropping the now-redundant per-package `typecheck` for tsc-built packages (`tsc --build` already typechecks) is the smallest graph but the largest design call. **Do not dismiss a repeat as a flake** — the signature is *all* exports of one workspace package missing simultaneously, and rerunning hides it every time.
