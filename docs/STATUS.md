- **Prototype ↔ data-model mismatches (adapt the model to the UI, not only the UI to the model)** — the Phase 5 design records **seven** places where the mobile-v1 prototype asks for something the domain/seam cannot express, and each is currently resolved by contorting the UI. That is the right default for a presentation rehaul but not automatically the right answer: several exist only because the domain was shaped for the desktop product's information architecture. Ledger (spec §8, with per-item workaround vs. model-change): **M1** sell-side has no "quotes I submitted" history projection; **M2** `CreateRfqInput.dealerIds` is required though the prototype has no dealer-picker; **M3** RFQ window is 120 s in the domain vs 45 s in the prototype (a 120 s ring barely moves on a phone); **M4** equities has no tick-history stream, so sparklines must be derived from OHLC candles; **M5** a fill is only a binary animation intent, with no order-lifecycle event carrying qty/price/outcome; **M6** `AnalyticsSimulator` emits the same frozen `STATIC_POSITIONS` constant on every emission, and **two of the Analytics screen's three widgets read it** (pair P&L bars, exposure bubbles) — so both the bars' 800 ms tween and the bubbles' 900 ms breathing would fire once on mount and never again, leaving most of 5c's motion work observable only inside a pinned golden; **M7** analytics history appends every 10 s against the prototype's 1 s mock cadence. **M6 is the one to weigh first** — cheap, confined to a simulator, and it decides whether most of 5c's motion work is worth doing at all. None of these are in Phase 5's scope; each is a candidate follow-up that would let a later pass *simplify* the UI rather than keep working around the gap. **All seven are SHARED, not RN-only** — every one lives in `@rtc/domain`/`@rtc/client-core`, below the UI and above both clients, so a model fix serves web and RN at once (the web analytics bars read the same frozen `STATIC_POSITIONS`; web merely never animates them, so nothing visibly fails to move). By contrast the *rendering* wrinkles — Reanimated worklets, regular-weight-only Skia text, unported `shadowBlur` bloom, the dev-client/simulator dependency — are RN-only with no web analogue. **Separately tracked as R1 (a gap against the REFERENCE implementation, not the prototype):** Adaptive's ReactiveTraderCloud analytics **exposure bubbles are draggable** (force-directed sim + drag behaviour); ours are inert in **both** clients — verified: no pointer/mouse/touch handler anywhere in `client-react`'s (or `client-solid`'s) `PositionsPanel`, and RN's are a static shelf-packed layout. Dragging is interaction, not decoration — it is how a user pulls a crowded bubble out to read it, most valuable exactly where our layouts are weakest. Cheaper than first recorded: an earlier draft claimed drag threatens pinned goldens — **that was wrong**. What threatens a golden is a force-directed simulation *settling over time*, not drag; a golden never drags, so an un-dragged layout is exactly as stable as today's (and the harness could disable drag outright). Keep the deterministic shelf-packed layout and add drag on top. The equivalent `loginWaitVariant` case was fixed on the login-wait-feedback branch (it awaits hydration via `vi.waitFor` before asserting); these two pre-existing peers were deliberately left as out of scope for that branch. This matters more than usual for this adapter because `hydrate()` reads from a positional `Promise.all`, where a misaligned index would silently assign the wrong stored value to the wrong preference — and neither of these two tests would notice. Not spec'd.
- **`as T` assertions can silently mask a missing required field at a construction site.** On the login-wait-feedback branch, adding a required field to `AuthViewState` did not fail `pnpm typecheck` at two production sites — [`createViewModel.ts`](../packages/react-bindings/src/createViewModel.ts) and [`createViewModel.ts`](../packages/solid-bindings/src/createViewModel.ts) (react-bindings and solid-bindings respectively) — because each ended its default-state object literal with `as AuthViewState`. A type assertion only requires the two types to sufficiently overlap, and a narrower literal missing one property still overlaps the wider interface, so TypeScript accepted it silently. Both assertions were deleted on that branch (replaced with a direct structural literal, which does catch the omission there), but the same pattern may exist at other construction sites across the codebase, and wherever it does, a green `typecheck` is not proof every site was updated when a required field is added. Worth a repo-wide survey and possibly a lint rule or grep-gate; not attempted, not spec'd.
- **Blank line between adjacent multi-line "block" statements — PARKED (investigated, no rule adopted).** Spun off from the `rtc/newspaper-order` extension (PR #287) that now pushes `jest.mock`/`jest.unmock` below the tests like `vi.mock` (both are hoisted above imports by their runners, so position is behaviour-neutral). The newspaper autofix already *separates* the mocks it moves (it joins them with a blank line), but there is **no rule that enforces a blank line between adjacent multi-line blocks in general** — e.g. two `jest.mock(…, () => {…})` factories authored already-at-the-bottom, packed with no separator. Goal was a *generic, size-based* rule ("if a statement spans more than ~2–3 lines, separate it"), **not** an identifier-based mock-only one. Findings: **(1) Biome cannot do it** — the maintainers deliberately don't implement `padding-line-between-statements`; blank-line *insertion* is classed as formatting, and the Biome formatter only preserves/collapses blank lines, never inserts required ones ([biomejs/biome#3016](https://github.com/biomejs/biome/discussions/3016)). **(2) ESLint can, via the existing `padding-line-between-statements`** (already in `eslint.config.mjs`): the `multiline-expression` selector matches exactly the missing case — multi-line call statements ending in `)` (like `jest.mock(…)` / `describe(…)`) that the current `multiline-block-like` clause misses because they don't end in `}`. Config would be one clause: `{ blankLine: "always", prev: "multiline-expression", next: "multiline-expression" }`. **(3) But its blast radius is large and imprecise** — measured on the repo it flags **350 spots across 152 files** (120 test, 32 production), all autofixable, with two false-positive modes: **(a)** simple statements that merely *wrapped* because they were long (e.g. a 3-line `expect(headers.get("CT")).toBe("application/json")`) get split from the next assertion — same spirit as the "don't separate one-liners" objection; **(b)** production RxJS assignment chains (`this.x$ = src.pipe(…)`) get separated field-by-field. Root cause: no built-in selector expresses *"a call whose **argument** is a real block / object-literal body"* — `multiline-block-like` keys on a trailing `}`, `multiline-expression` on any 2+-line span; the granularity is binary (single- vs multi-line), with no line-count threshold. **Options if revived:** (i) accept the generic `multiline-expression` clause (repo-wide, or scoped to `**/*.{spec,test}.{ts,tsx}` to spare production RxJS) and live with the wrapped-statement noise; (ii) write a small autofixable custom `rtc/` rule that fires only between multi-line statements whose body is an actual block/object-literal (exempting merely-wrapped ones) — precise, matches the "block" intent, but new code to maintain; (iii) do nothing and rely on the newspaper-order autofix for the common (moved-mock) case. **Parked** until it recurs / annoys enough to justify option (i) or (ii).
